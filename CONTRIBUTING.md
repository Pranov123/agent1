# Contributing to Agent 1

Thank you for your interest in contributing. This document explains how to get set up, how the codebase is structured, and what good contributions look like.

---

## Getting Started

### 1. Fork and clone

```bash
git clone https://github.com/YOUR_USERNAME/agent1.git
cd agent1
```

### 2. Set up your environment

```bash
python3 -m venv env
source env/bin/activate       # Linux / Mac
# env\Scripts\activate        # Windows

pip install openai pydantic rich
```

### 3. Add your Groq API key

Open `config.py` and replace the placeholder:

```python
GROQ_API_KEY = "your-groq-key-here"
```

Get a free key at [console.groq.com](https://console.groq.com).

### 4. Verify the setup

```bash
python3 -c "
from core import get_client, get_primary_model
client = get_client()
r = client.chat.completions.create(
    model=get_primary_model(),
    messages=[{'role':'user','content':'say ok'}],
    max_tokens=5
)
print('Setup OK:', r.choices[0].message.content)
"
```

### 5. Run the agent

```bash
python3 main.py
```

## How the Pipeline Works

```
User input
    │
    ├── Stage 1A: Requirement Extractor      (Llama3 / Qwen3)
    ├── Stage 1B: Ambiguity Detector         (Llama3 / Qwen3)
    ├── HITL 1:  Intent Checkpoint           (Human)
    ├── Stage 1C: Requirement Enrichment     (Llama3 / Qwen3)
    ├── Stage 2:  Scope Definition           (Llama3 / Qwen3)
    ├── Stage 3:  Validation Layer           (Llama3 / Qwen3)
    └── HITL 2:  Scope Approval             (Human)
```

Each stage has its own system prompt defined inside `core/pipeline.py`. The prompts are the most important part of the system — changes to them have the biggest impact on output quality.

## Ways to Contribute

### Prompt improvements

The system prompts inside `core/pipeline.py` are the core of the agent. If you find a case where a stage produces incorrect or low-quality output, the fix is almost always in the prompt.

Each prompt follows this pattern:
- A clear job description
- Strict rules with examples of good and bad output
- A precise JSON output format

When improving a prompt:
1. Test with the individual stage script in `prompts/` first — faster iteration
2. Verify with `python3 main.py` end-to-end once the stage passes
3. Test on at least 3 different input types (consumer app, hardware, internal tool)

### New validation checks

Stage 3 validation checks live in the system prompt. To add a new check:
1. Add it to the numbered check list in the Stage 3 system prompt
2. Add the corresponding field to the output JSON schema in the prompt
3. Add a display method in the `Displayer` class in `pipeline.py`
4. Add flag application logic in `_apply_validation_flags`

### Artefact generator improvements

The markdown artefact is generated by `core/artefact_generator.py`. Each section is a separate method. To add a new section:
1. Add a `_build_<section>` method
2. Call it in the `generate` method in the right order
3. Keep sections self-contained — each method should only use `self.session` data

### State machine extensions

New states and transitions live in `core/state_machine.py`. The `TRANSITIONS` dict defines all valid paths. When adding a new state:
1. Add it to the `STATES` list
2. Add all valid transitions to `TRANSITIONS` with the correct actor (`system` or `human`)
3. Update the `SessionManager` if the new state requires new metadata fields

## Contribution Rules

### Never commit API keys

A pre-commit hook blocks commits containing Groq API key patterns. If you need to test with a real key, keep it in `config.py` only — this file is tracked but should always contain the placeholder before committing.

Before every commit:
```bash
python3 -c "
import re
with open('config.py', 'r') as f:
    content = f.read()
content = re.sub(r'<groq-key-pattern>', 'your-groq-key-here', content)
with open('config.py', 'w') as f:
    f.write(content)
print('Key cleaned')
"
```

### Test on multiple input types

Every change should be verified against at least:
- A consumer mobile app idea
- A hardware / IoT product
- An internal business tool

These three types exercise different parts of the pipeline and expose different failure modes.

### Keep prompts evidence-based

The validation layer must never speculate. Any new validation check must:
- Require direct evidence from the scope before flagging
- Reference specific requirement UIDs in every finding
- Not flag generic risks that apply to every product

### Commit message format

```
<type>: <short description>

Types: feat, fix, prompt, refactor, docs, chore
```

Examples:
```
feat: add sensor calibration check to Stage 3 hardware validation
fix: remove false dependency between reminder and sync requirements
prompt: improve Stage 1C acceptance criteria measurability rules
docs: update README walkthrough to include Stage 1C
```

## Swapping Models

The agent is model-agnostic. To swap models, edit `config.py`:

```python
# Using Groq (default — fast, free)
GROQ_PRIMARY_MODEL    = "llama-3.3-70b-versatile"
GROQ_VALIDATION_MODEL = "llama-3.3-70b-versatile"

# Using a different Groq model
GROQ_PRIMARY_MODEL    = "mixtral-8x7b-32768"
GROQ_VALIDATION_MODEL = "llama-3.3-70b-versatile"
```

Available Groq models: [console.groq.com/docs/models](https://console.groq.com/docs/models)

For local models via Ollama, update `core/__init__.py` to point at your local endpoint.

## Reporting Issues

When reporting a bug or bad output, include:
1. The raw input you gave the agent
2. Which stage produced the incorrect output
3. What the output was
4. What you expected instead
5. The session JSON from `output/` if available

This gives enough context to reproduce and fix the issue quickly.
